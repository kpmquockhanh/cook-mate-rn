topic: Closing the capability gaps in the CookMate crawl engine, including extraction from unstructured recipe pages
created: 2026-09-18
---

- `event` Spec created from a code read of `backend/src/crawl/` and the stages downstream of it. No prior spec existed for this engine.
- `note` No BMad install in this repo (`_bmad/` absent), so config could not be resolved; spec folder placed at `docs/specs/spec-crawl-engine/` alongside the existing `docs/prd.md` and `docs/brief.md`.
- `note` Engine as read: `discover` → `crawl_queue` → `raw_pages` (immutable) → `recipe_staging` (parse → enrich → gate) → `public.recipes`, driven by `src/cli.ts` verbs and the in-process job runner behind the operator console.
- `direction` User asked what happens when the engine is pointed at a plain-text food blog with no schema.org markup, then directed that all missing capabilities be captured.
- `decision` Answered: the engine crawls it and drops it. Tiers A/B/C all miss, `raw_pages` keeps the HTML with `extracted = null`, and `parse` filters on `extracted is not null` so it never reaches staging. On the `discover` link-walk path the HTML is discarded entirely because `ingestFetchedPage` is guarded by `if (recipe)`.
- `decision` Unstructured extraction becomes a first-class capability (Tier D, LLM over stored HTML) rather than a variant of the existing adapter tier, because adapters are per-domain selectors and this must generalize across unseen blogs.
- `constraint` Tier D reads stored `raw_pages` HTML only and never triggers a fetch, so it re-runs over the corpus offline exactly like `enrich` does today.
- `decision` Discovery must ingest every page it fetches, not only the ones that already parse, otherwise Tier D cannot run without a second crawl of the same source.
- `capability` CAP-1 robots.txt compliance correctness — the `$` end-anchor is dead at `crawl/robots.ts:78` and user-agent group matching is both too loose and non-unioning at `:59`.
- `capability` CAP-2 true per-host pacing — `crawl/fetcher.ts:22` releases the gate from request start, not completion, so the documented one-in-flight-per-host invariant does not hold.
- `capability` CAP-3 recrawl and freshness — `crawl_queue.url_hash` is globally unique and `enqueue` is `on conflict do nothing`, so a URL that reached `done` can never be re-queued; a source updating a recipe is invisible.
- `capability` CAP-4 conditional requests and backoff — no ETag/Last-Modified is stored, and `fetchWithRetry` ignores `Retry-After` on 429/503 in favour of a fixed 2s/4s backoff.
- `capability` CAP-5 stale lock recovery — `crawl_queue.locked_at` is written at claim time and never read, so a crash strands rows in `fetching` permanently.
- `capability` CAP-6 Tier D LLM extraction for unstructured pages — the plain-text food blog case.
- `capability` CAP-7 rendered-page fetching for JavaScript-built recipe pages.
- `capability` CAP-8 discovery reuse of fetched HTML and awareness of already-crawled URLs — `seen` is in-memory only, so a second run re-fetches pages already in `raw_pages`.
- `capability` CAP-9 bounded raw-page storage — `raw_pages.html` is uncompressed full HTML with no retention policy, and is the table that will dominate the database.
- `capability` CAP-10 crawl run observability — `extractionReport()` is the only signal, so run-over-run regression is not answerable.
- `capability` CAP-11 test coverage for robots and fetcher — `test/` covers discover/parse/enrich/api/auth and nothing exercises the two modules carrying CAP-1 and CAP-2.
- `capability` CAP-12 gzipped sitemap support — `crawl/discover.ts:216` checks for `.gz` after the fetch has already completed, paying for a download it then discards.
- `constraint` Every tier must emit `ExtractedRecipe` so the deterministic `parse` stage is unchanged by any of this.
- `constraint` Politeness stays single-sourced: discovery and crawl must keep sharing one robots reader and one fetcher rather than growing a second implementation.
- `constraint` `crawler.sources.allow_image_use` keeps defaulting to false and no new code path may flip it.
- `assumption` Single-process crawling with `FOR UPDATE SKIP LOCKED` remains sufficient; nothing here assumes a distributed fetcher.
- `question` Which model and per-page budget cap for Tier D, and does Tier D output route straight to `review` rather than `approved`?
- `question` Is CAP-7 (headless rendering) wanted now, given it puts Chromium in the backend image, or deferred behind a per-source opt-in?
- `question` What drives recrawl cadence — a fixed per-source interval, or sitemap `lastmod`?
- `question` Retention target for `raw_pages.html`: compress in place, offload to object storage, or drop HTML once a row has been published?
- `event` Self-validate pass 1 (coherence): pass. All twelve capabilities carry intent and success; four unresolved gaps recorded as open questions rather than invented.
- `event` Self-validate pass 2 (preservation): pass. Every defect and gap named in the code read landed in SPEC.md or `current-defects.md`. No wrapper-only content dropped.
- `decision` CAP-7 (rendered-page fetching) is deferred. Read as out of scope for this spec rather than built-behind-an-off-flag; it moves to Non-goals and CAP-7 is retired, never reused. The Tier E shape stays documented in `extraction-tiers.md` so the slot is reserved rather than forgotten.
- `decision` Recrawl cadence for CAP-3 is a fixed per-source interval, expressed as source policy on `crawler.sources` alongside `crawl_delay_ms` and `allow_image_use`. Sitemap `lastmod` is not the driver.
- `decision` CAP-9 is solved by offloading raw HTML to object storage, with `crawler.raw_pages` keeping the reference and the content hash.
- `constraint` Superseding the earlier Tier D constraint: Tier D must not fetch from the *source site*. Reading our own object store is expected and permitted, because CAP-9 moved the HTML there. The earlier "never triggers a fetch" and "no network access" wordings are withdrawn as now-contradictory.
- `assumption` Object storage means Supabase Storage, since the project already depends on Supabase for auth and the app tables. No separate provider is assumed.
- `event` Re-derived SPEC.md and both companions from this log. Eleven live capabilities; one open question remains.
- `direction` User asked for a story breakdown of the spec.
- `decision` Six stories, in execution order: (1) robots/pacing correctness with tests, (2) discovery fetch reuse, (3) raw HTML to object storage, (4) Tier D extraction, (5) freshness, (6) run observability.
- `decision` Story 1 leads because correcting the robots `$` anchor and the user-agent match makes the crawler strictly more restricted; that exclusion should surface on a small corpus before freshness turns crawling into a recurring schedule.
- `decision` Object storage (story 3) lands before Tier D (story 4), so story 3 introduces the page-HTML accessor that Tier D consumes and Tier D is never written against the `raw_pages.html` column. Accepted cost: the prose-blog capability waits behind an infrastructure migration.
- `decision` Story 2 is sequenced before Tier D as a value multiplier, not a blocker — Tier D can be developed against pages the `crawl` path already stored with `extracted = null`.
- `decision` CAP-3, CAP-4 and CAP-5 stay one story: they share the queue/fetch lifecycle and one migration, and conditional requests have nothing to act on without recrawl.
- `decision` No story takes a spec checkpoint; the user declined human plan review on all six.
- `decision` Only story 1 takes a done checkpoint, so the effect of the stricter robots handling is inspected before anything builds on it.
- `event` stories.yaml written and checked against the schema's validity rules: six entries, ids unique, quoted, prefix-free, no status field.
- `decision` Story 1 implementation: robots.txt group selection now follows RFC 9309 specificity — the group matching our product token wins outright and `*` is the fallback, rather than the two being OR-ed. This goes beyond the three defects named in `current-defects.md` but is required by CAP-1's "correctly scoped user-agent groups": OR-ing them re-imposes a global rule that a site deliberately lifted for a named bot.
- `decision` Story 1 adds `crawl --robots-check`, a read-only audit that re-evaluates queued URLs against current rules and reports what is now disallowed, grouped by domain and flagging rows already fetched. It satisfies the story's dispatch note that the stricter reading must surface as a list rather than as silent skips.
- `event` Story 1 complete: `robots.ts` rewritten around parsed groups with a pure `parseRobots`/`isAllowedBy` seam, `fetcher.ts` host gate now measures the delay from response completion, 17 new tests added, full suite 74 passing, typecheck clean. Done checkpoint reached — dispatch pauses here.
- `decision` Story 2: a discovery run that meets an already-stored page reads the stored copy instead of skipping the URL. Skipping outright was the first implementation and was wrong — it strands the link walk, because a hub page walked previously still carries the links the walk needs. `storedPage()` in `crawl/run.ts` is the read, and it is the natural seam for story 3's object-storage accessor to replace.
- `decision` Story 2 splits page storage from queue bookkeeping: `storeFetchedPage()` writes the raw page alone, `ingestFetchedPage()` also writes the terminal queue row. Discovery uses the first for hub pages it read only for links, so a category listing does not land in `crawl_queue` as a failure for a question nobody asked of it.
- `decision` Gzipped sitemaps are detected by the gzip magic number rather than by a `.gz` in the URL, which covers both `Content-Encoding: gzip` (already decompressed by fetch) and raw `application/gzip` bytes, and the servers that mislabel either.
- `decision` `discover --refetch` added as the escape hatch for re-fetching pages already stored, since reuse is now the default.
- `event` Story 2 complete: CAP-8 and CAP-12 delivered, 6 new tests, full suite 78 passing, typecheck clean. No done checkpoint on this story, so story 3 may follow.
- `decision` Story 3: pages are content-addressed by their existing `content_hash` and gzipped, at `<first two chars>/<hash>.html.gz`. Content addressing means the same HTML reached by two URLs is stored once and a re-store overwrites itself, so uploads are idempotent and need no coordination.
- `decision` The `html` column is dropped by its own migration (0007) that raises an exception while any page still holds unmoved HTML. `migrate` applies every pending file in one invocation, so an unguarded drop would add the reference column and destroy un-backfilled pages in the same run. Each migration has its own transaction, so the guard costs one extra operator command and cannot lose data.
- `decision` `storeRawPage` uploads before inserting the row, so a `raw_pages` row never references an object that does not exist.
- `decision` A filesystem driver (`RAW_PAGE_STORE=file`) sits beside the Supabase driver. It is not a second production target — deployments use Supabase Storage per the spec — but it keeps local work and the test suite free of a Supabase project, which is what allowed CAP-9 to be covered by the no-network suite.
- `assumption` The crawler authenticates to Storage with the service-role key against a private bucket, via the Storage REST API rather than `@supabase/supabase-js`. This matches the backend's existing style: it talks to Postgres through `pg` and verifies Supabase JWTs locally with `jose`, carrying no Supabase SDK.
- `event` Story 3 complete: CAP-9 delivered. `readRawPage` is the single accessor story 4 consumes, and it serves pages from either location during the transition. 5 new tests, full suite 83 passing, typecheck clean.
- `direction` User started story 4 without settling the open question, so it was implemented under stated, reversible defaults rather than blocking.
- `decision` Tier D model defaults to the same cheap workhorse enrichment uses (`EXTRACT_MODEL`, falling back to the provider's default model), because extraction is a comparable per-page task and a second provider configuration would be one more thing to get wrong.
- `decision` Budget is two ceilings: `--limit` for what the operator meant, and `EXTRACT_MAX_PAGES_PER_RUN` (default 200) that a mistyped limit cannot exceed. Listing-shaped URLs are filtered out by `classifyUrl` before any model call, and `EXTRACT_MAX_CHARS` bounds a single page's cost.
- `decision` Tier D output routes to `review` and is never eligible for `approved`, enforced in the gate by joining `raw_pages.extractor`. A misread quantity is indistinguishable from a correct one by score, so a human reads it first. This resolves the routing half of the open question.
- `decision` The provider layer was generalized from `EnrichmentSchema` to a schema passed per request, so enrichment and extraction share one provider stack rather than growing two.
- `decision` Tier D records a verdict even when it finds no recipe: `extraction_version` is stamped while `extractor` stays `'none'`, so the page still reports as a miss but the next run does not pay to reach the same conclusion.
- `decision` A grounding check rejects output whose ingredient lines do not appear in the page text, matched on content words to tolerate the light reformatting the prompt permits. The schema cannot catch a well-formed recipe for a dish the page never mentions, and that is the failure mode that would put fabricated food in front of users.
- `decision` Images come from the page's own `og:image` and content `<img>` tags, never from the model, so no image URL can be invented.
- `event` Story 4 complete: CAP-6 delivered, 8 new tests, full suite 91 passing, typecheck clean.
- `decision` Story 5: `recrawl_interval_hours` defaults to 720 (30 days) rather than NULL. Conditional requests make an unchanged revisit nearly free, so an on-by-default schedule is what makes CAP-3 mean anything without per-source configuration; NULL disables it per source.
- `decision` The refresh sweep runs inside `crawl`, bounded by the same `--limit`, and gives refreshed rows a worse priority (200 vs 100) than new URLs. An unbounded sweep would turn one run into a full re-crawl of the corpus.
- `decision` Only `done` rows are revisited, not `failed` ones. A page that failed has already spent its attempts, and rediscovering that monthly is waste.
- `decision` `Retry-After` closes the whole host, not just the refused request, via a per-host penalty the gate honours both before a queued request runs and when releasing to the next one. Honouring it on the retry alone would keep hammering a host with every other URL behind it.
- `decision` `parse` now selects the latest `raw_pages` row per URL and treats a row as pending when staging was not built from *that* row. The old `not exists (staging where url_hash)` test could never be false once a URL had been parsed, which is the reason a changed recipe needed `--force`.
- `decision` A new raw page behind an existing staging row clears that row's enrichment. The enrichment was not merely stale but wrong — its timers and step-to-ingredient indices point into a steps array that no longer exists. A re-parse of the same page (`--force`) keeps enrichment, so improving a parser does not re-buy the corpus. This was not in the story's scope and was found while tracing what a changed page does after `parse`; without it a changed recipe would reach the gate unenriched and be rejected.
- `event` Story 5 complete: CAP-3, CAP-4 and CAP-5 delivered, 4 new tests, full suite 95 passing, typecheck clean.
- `decision` Story 6: counters live in a `jsonb` column on `crawler.crawl_runs` rather than typed columns, because crawl, extract and discover count different things and adding a counter should not need a migration.
- `decision` Counters are flushed on a 5-second timer as well as at the end, since a run that dies is the run whose numbers matter most. The timer is `unref`ed so a pending flush never keeps a CLI command alive.
- `decision` Both the CLI and the console render runs as a matrix — counters down, runs across, oldest on the left — rather than a block per run. The capability is a comparison, and a trend is not readable when the runs are stacked vertically.
- `decision` A counter absent from a run renders as a dash, never as zero: "this counter did not exist yet" and "this counter counted nothing" are different findings.
- `decision` Deltas in the console are not coloured red/green. More `http_304` is good and more `failed_no_markup` is bad, so colouring by direction would tell the operator the opposite of the truth about half the counters. The sign carries the meaning.
- `decision` 5xx statuses bucket into one counter while other statuses stay exact, because every 5xx calls for the same response and one counter per code would spread a single outage across several names.
- `event` Story 6 complete: CAP-10 delivered, 4 new tests, full suite 99 passing, typecheck clean.
- `event` All six stories in stories.yaml are implemented. Every capability in SPEC.md except the retired CAP-7 has been delivered.
- `event` First real crawl against a prose blog surfaced two defects in the interaction between the revisit machinery (story 5) and Tier D (story 4), neither visible until both existed.
- `decision` `storeRawPage`'s `on conflict` clause now only overwrites `extracted`/`extractor` when the incoming extraction actually found something. Re-fetching a page whose content is unchanged but which sent no validators lands on the same `(url_hash, content_hash)` row with a fresh `'none'` from tiers A-C; the previous clause assigned that unconditionally, erasing a Tier D extraction while `extraction_version` stayed stamped, so Tier D would never re-read it. The recipe vanished on the first revisit and could not come back.
- `decision` When Tier D extracts a recipe it flips that URL's `crawl_queue` row from `failed` to `done`. The `failed` verdict came from tiers A-C missing and is out of date once Tier D has read the page; more importantly the revisit sweep only refreshes `done` rows, so leaving it would have silently excluded every prose-only recipe from ever staying fresh.
- `decision` `crawl` now logs a page with no structured markup at info level as "kept for extract" rather than warning "no recipe markup found", and prints a closing hint naming the command. The queue row still goes to `failed`, which on its own reads as though the page were lost when it is in fact the input Tier D exists to read.
- `event` A transient DNS failure against the Supabase pooler exposed two latent faults in `src/db.ts`, neither of them caused by this spec's work.
- `decision` The `pg.Pool` now has an `error` listener. An idle client whose connection drops makes pg emit `error` on the pool rather than on any query, and Node treats an unhandled `error` event as fatal - so a network blip could take down the console or the API instead of costing one reconnect.
- `decision` `connectionTimeoutMillis` moved from a hard-coded 10s to `DB_CONNECT_TIMEOUT_MS`, defaulting to 30s. A healthy connect to the observed ap-southeast-2 pooler takes about 7s, so the old ceiling turned ordinary latency into failed requests; a timeout shorter than a healthy connect protects nothing.
